- scope: the aim is to provide some background and a mindset that I find useful when interacting with an agent, which I think is the prerequisite for the huge productivity gains one can get, in particular compared to using it purely as a chatbot. I mostly think of the use case of an economist working on research, but most principles translate to many other use cases. the idea is to keep it as plain and easy as possible and avoid technical lingo. there is a lot of hype around advanced features (agent skills, GitHub integration, ...) which most people will simply not need: following the basic principles sketched here gets you maybe 90-95% of what you can get out of agent usage. so start here, without additional features, and you'll get very far already.
- disclaimer: these are my impressions and what works for me. this is not an exact science, so adjust it to whatever workflow and software setup works best for you. these are meant as basic guiding principles and a basic mindset, not a fixed recipe.
- prerequisites: any basic subscription (Claude, Gemini, OpenAI Codex, ...) at around 20 USD/month should do. the free versions might not be sufficient, but you almost certainly will not need the 200 USD (or similar) versions - if you do, you're probably way ahead of what's covered here anyway. which provider you pick is not that relevant: any subscription you have will get you started.
- Difference chatbot vs. agent: chatbots needs copy/paste; short-lived (no real context); can't interact with your local files (so e.g. you manually need to copy/paste all grammar mistakes back to your document); agent: interacts with local files (including writing into all of them); has access to entire context you provide;  does tasks on your behalf (and identifies which subtasks are needed on its own -> planning and reasoning)
- ``coding agent'': the terminology is misleading; almost every interaction you make with your computer can be thought of as ``coding''. e.g. writing plain text in a document. formatting a document. reading a document, calculation in excel. extracting content from one file and bring it in context with respect to others. conceptualize. 
- ``coding agent'' misconception 2: the wording might suggest it's for empirical projects only, but that's not at all the case. agents work perfectly as RAs for admin and writing tasks, and also for theory work, given the big improvements in math capabilities over the past year or so. e.g., once you have a proposition, ask the agent to verify that everything is in place (check what you've been doing). or, if you have notes or a sketch of your analysis (e.g., what you think characterizes the equilibrium), the agent is typically quite successful in bringing this into a proper paper-like format, e.g. turning your notes into a proper proposition. again helpful: provide a sample of what such a proposition should look like in your field.
- background: every operation can (and should!!!) be scripted. (TODO give some examples here? e.g. grep/awk/sed). you might not be aware, what would be good examples here?, don't think of it as clicking through, rather: what is the real operation behind this? related: everything is a file
- file formats: plain text vs binary formats: (TODO better explanation??) plain text files are e.g. .txt, .md, .csv, .R, .py, .do, .tex. binary formats are pre-compiled or used for storage of other data (e.g., .jpg, .png, .mp4, .docx., .xlsx, .pdf, .dta). just to give it a try, open a pdf or docx in NotePad or TextEditor - you'll see lots of characters which aren't directly meaningful to a human reader. note that even binary files tend to be much larger: e.g. the compiled PDF based on a (plain text) tex file can easily exceed a few MB, even when the tex file was just a few KB. basic rule: anything you actively work on has to be plain text based (code, .tex, .md). binary formars should be reserved for pure input (e.g. related literature, funding information, xlsx/docx from external sources), and for pure output (e.g. generated a PDF at the very end). main reasons: plain text is so much closer to the basic unit of information for LLMs, and so much easier for them to work with and interact: a human might not care whether they open an XLSX or CSV file in Excel, and then try to find the GDP for Austria in 2020 within them. For the LLM it's way different: XLSX entails decoding first, which is relatively slow, lengthy in costly in terms of tokens; whereas the CSV is readable right away, and a few grep/awk calls deliver the required number extremely fast. so working with plain text is orders of magnitudes faster and cheaper in terms of tokens. it's also so much easier and faster for LLM to overwrite .tex (and the possibly generate a PDF at the very end) as opposed to writing in DOCX or XLSX). (finally, plain text also lends itself very naturally towards tracking the progress of a document over time, e.g., what did person X change or amend on date Y relative to the previous version, and why? so the growth of a project is much more visible, even if you only use e.g. dropbox which also stores a document history, as opposed to richer features through github)
- mindset (probably we need to break this up into subparts later): your agent as your personalized research assistent (RA). extremely capable provided the context you give. your job: provide your context and background (e.g., your RA might be extremely strong in math but have a physics background: you need to make clear how you use certain terminology). provide clean instructions and set expectations about output, and how to proceed if anything is unclear (e.g.: ``NEVER EVER make assumptions, ALWAYS clarify with me beforehand'', or: ``proceed as far as you can given my input. leave a TODO note in the document for me for anything that is unclear at this stage, so we can come back to it later''). most importantly: this is your RA - RAs may make mistakes or misinterpret input. as for any RA, you remain in charge for the final output. you absolutely have to make sure to keep safeguards about the output, and verify at length at the end (read, check, ..). you can instruct another AI RA to cross check the final product for you, but most of it will remain your responsibility. make sure to leave enough time for that at the end. AI slop shows!
- mindset 2: project = folder: agents think in terms of ``projects'', the basic unit for the entire context and workflow, where project equals a folder in your local file system. in this folder, you should store all needed background information (e.g., /literature), code (/code), data (/data), your writing samples (/samples), instructions, and status (agent log files). this will also be the folder you'll come back to. many of these ``projects'' might be rather short lived
- mindset 3: copy/paste = friction = bad! you should never be required to copy/paste. when your agent needs input, point it to the location in the folder (e.g.,: consider document X in the literature folder, or: consider paragraph 3 in my paper, or line 142 in my tex). when the agent generates reusable output, it should be directly in the final text (e.g. once you're confident that slide 17 is fine as discussed, you can tell your agent to write this in the tex file. it will find where this should be). avoid copy/pasting output from the chat window into your documents!
- mindset 4 (related): every final output should be fully scripted: your R/Python/Stata code should generate production-ready tables as .tex, which you include via \include or \input in your main document. never ever change these tables manually, never ever copy/paste them into your document. throughout the project, you'll redo the same table 10 more times, so save yourself the effort of changing row lables, order, formatting, .. each and every time and make sure the tables already come out properly from your code. the objective should be: every exhibit, every calculation, ... needs to be in a script!
- example of that mindset: if you already have a target table layout, just tell your agent to *change* your code to match that layout in the code *that generates it*. DO NOT tell the agent to adjust the table layout in your final text - this would be a one-time overwrite which you would be required to redo next time (which kills reproducability and is error prone). 
- example 2: do NOT tell your agent in the chat window to "compute what these numbers mean", and then copy/paste the result into your document. instead, tell your agent to include this very calculation in your code, and then incorporate the result in the document.
- fallibility: contemporary LLMs are trained on basically the entirety of human written knowledge, so within a certain domain they can be thought of as having almost superhuman capabilities of understanding and reading between the lines. but to harness these for your particular project, you need to provide the context: clear instructions and clear background. that's your main job, and then you should typically expect really good results. still, it remains a tool, and it might occasionally forget: over time, the context window keeps growing, and there might be partially contradictory instructions. so don't take for granted that everything you ever wrote or instructed will be respected forever. occasionally ask it to refresh its memory or double check.
- sparring partner: besides using it as an RA, I frequently use the agent as a sparring partner for ideas. e.g., I come up with an idea or interpretation (``I think we should adjust the discussion in our paper in this and that manner''), and then ask the agent to critically assess and deliberate this with me: does this line of reasoning work relative to what we've written elsewhere, and relative to what others have written already? (risk: something written towards the end of a paper might be partially contradictory with what's elsewhere.) this back-and-forth often points out something I might have overlooked. think of it as doing your homework and a first sanity check before bothering another human, i.e., strengthening your arguments before suggesting them to your colleagues.
- asynchronous work: a big advantage of the RA interpretation is the possibility of working asynchronously on longer tasks. you can easily launch 3, 5, 10 agents on different projects and let them run in the background (half an hour, a few hours, overnight, over the weekend, depending on scope), and only reconcile once they're finished. to make this work, set a clear scope for the next set of instructions up front: ask the agent to plan the subtasks involved and to clarify on the spot whether any questions are left or whether the instructions are clear. anything unclear should either be clarified right away, or handled by reasonable assumptions, or left as a TODO for later. what to avoid: the agent runs for an hour, then comes up with a question and cannot proceed on the main tasks without your input. so make all decisions up front (or defer non-critical ones), let a few agents run simultaneously while you do something else, and come back once they're done. there will also be times when you work interactively with one agent on a certain part, but most tasks should rather be asynchronous.
- instructions.md: the basic unit of how you set up the work with an agent: think of it as a contract between you and the agent. in contrast to chatbots (where there's a lot of discussion about lengthy, creative, page-long prompts), the starting point is a file, typically called instructions.md, which sets up the basic contract and scope of the project. my typical structure:
  - scope/expectations: e.g., ``we are working on a research paper in economics'', or ``we are preparing the teaching slides for a bachelor level course in digital economics''
  - related literature: e.g., ``take into account and read the background literature in the /literature folder''
  - for longer projects: expected tasks, sub stages of the project, and how we proceed and interact
  - main expected output file: e.g., ``in the end, we need a document called paper.tex, this is our main document''
  - software (if applicable): which software we use, in which folder the code is, which input and output files to take into account
  - style guide: I found it very helpful to provide a writing sample of my own (some paper or document I've written in the past). this sets both the basic style (layout conventions, format of the document) and my language and tone, which the agent should adhere to
  - checks: at the very end (or whenever I instruct it to in between), do a thorough grammar check, internal consistency check, language check, style check, ...
  - logging (for longer projects): ``at the end of each session, whenever we've made major changes, or whenever I instruct you to, keep track of what we're up to in status.md. when we restart a session, read it first'', so we don't need to start from scratch each and every time
- instructions.md 2 (structure): this is not an exact science, there is a huge amount of freedom. big difference to e.g. programming in Python, where you absolutely have to adhere to syntax requirements. so no need to overthink the precise wording, LLMs are perfectly capable of extracting what you meant. it also doesn't matter much whether you provide it as .md or .txt or whatever. my impression is there's some advantage to providing at least a little structure (e.g. subsections in an MD file), but a plain text file with sections 1, 2, 3 will be perfectly fine as well.
- instructions.md 3 (why bother): spend a little time on it. not on the precise formulation, which doesn't really matter, but as opposed to writing a one-off prompt, it forces you to think clearly about the different sub steps involved in the project. no need to overthink it either, you can extend and amend it later. but for most projects it's helpful to take at least 10-15 minutes and write down: what's the related background, what's the setup, what are the expected deliverables, what are the sub steps and sub stages? this gives you clarity, and also clarity in your communication, i.e. the contract with your RA: what is the RA expected to do?
- hallucitations: I usually include an instructions section saying the agent must NEVER EVER cite (i.e., add a LaTeX reference via the .bib file) any document that is not in my /literature folder. a bit tedious, but it keeps me in control of which documents get cited, and when. I frequently let the agent recommend potentially related literature, but then I always look up the original papers myself, download them and put them into /literature, and only from there on the agent may cite them. this ensures I always have the real and latest versions (otherwise there's a risk the agent keeps working with an outdated working paper version), and avoids citing something I wouldn't have wanted to cite, or which doesn't even exist (which still remains an issue).
- token usage: my impression so far is that the 20 USD version should be more than enough for most people's daily usage, unless you have a really lengthy and involved coding project (out of scope here). people tend to run out of tokens quickly for one of two reasons: (1) lots of parallel online querying tasks (e.g., the agent launches 20 subagents in parallel to query real online information), which eats lots of tokens. occasionally helpful, but only use this when really needed, and then provide a tighter context to begin with. (2) working with binary formats as opposed to plain text. if you mostly use plain text as suggested above, token usage drops radically and should typically be fine.
- effort: medium for most tasks. regarding reasoning effort and which (fanciest) LLM version to use: for what most of us are doing, it really doesn't matter that much. pick whichever version works for you, no need to overthink or chase each and every trend, there are so many changes all the time. effort is basically a trade-off between response time and token usage. for most state-of-the-art versions, medium effort is perfectly fine (reasonably fast, reasonably low token usage). if you really want to thoroughly check something, occasionally switch to high effort, but typically this shouldn't be needed.
- putting it together (the basic jump start): there are really just a few elements. the basic unit is a folder. put whatever background files you need for the project into that folder (related literature subfolder, your writing sample, your first draft, ...) and an instructions.md file where you sketch your basic ideas. that should be your mindset whenever you start a project. then open Claude Code (or whatever), tell it to read the instructions, and take it from there - you'll be good to go.
